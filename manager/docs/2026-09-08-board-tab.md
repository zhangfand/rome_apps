# Manager Board tab

Status: implemented 2026-09-08.

## Why

Manager already owns execution: a person's Created fact is reconciled into a
detached `run_worker`, and every position is folded from the append-only facts
ledger. Dev Desk separately offered the useful GitHub planning view. Keeping
dispatch in both places would create two definitions of “in progress” and two
concurrency mechanisms.

The Board brings the proven GitHub snapshot into Manager and makes the ledger
the join point. It supersedes Dev Desk for GitHub planning without importing
Dev Desk's claims, leases, chats, Linear provider, or agent-turn hook.

## Stored read model

Two tables are deliberately not task state:

| Table | Purpose |
|---|---|
| `manager__snapshots` | Latest successful GitHub snapshot, keyed by `owner/name` |
| `manager__preferences` | Guardian's selected repository |

A snapshot is written only after the complete sync succeeds. An error keeps the
prior row intact. The API response surfaces the error and the web tab continues
to render the cached snapshot. GitHub Projects scope failures explicitly ask
for a reconnect with `read:project`.

Sync uses `connector:connector_proxy` with toolkit `github`; Manager never sees
or stores a token. It reads:

- Projects v2 linked to the selected repository as epics;
- every issue project item, including cross-repository items;
- open repository issues on no project into a synthetic “No project” epic;
- native `blockedBy` plus references under an issue body's `## Blocked by`;
- issue closing PR links plus closing references found on repository PRs;
- issue, project, and PR state.

The persisted shape retains a `provider: "github"` discriminator so another
provider can be added without changing every consumer. There is no Linear code.

## Pure join

`src/lib/board.ts` takes a GitHub snapshot and `LedgerSnapshot` and returns the
Board state:

| Column | Rule |
|---|---|
| Ready | issue is open and every known blocker is closed |
| In Progress | issue is open and an open ledger task's Created brief names it |
| Blocked | issue is open with a known open blocker |
| Done | issue is closed |

Issue matching uses `issueRefsIn`, including its de-duplication rule, then
normalizes the repository key case. In Progress carries the matching task id,
folded position (`working`, `stuck`, `reported`), and live worker id. Worker
session links come from the existing dashboard read model.

## Implement

`POST board/implement { issueId }` trusts issue metadata only from the selected
saved snapshot. It requires Ready and returns `409` if any non-terminal task
already names the issue. It creates no fact directly. Instead it invokes:

```text
manager:create → manager:reconcile → manager:run_worker
```

The brief comes from the exact `briefFromIssue` helper labeled intake uses, so
title, body, GitHub URL, branch/PR delivery terms, and issue-close completion
semantics cannot drift. The fact source cites the URL and says “Implement
pressed on the board”.

## Refresh

The Board can refresh on demand and periodically. Reconcile also refreshes,
after intake, the selected repository plus every `intakeRepos` entry. Each
repository is best-effort and logged independently; no failure blocks issue
close observation, ledger decisions, or worker launch.

## Routes

- `GET board/repositories`
- `GET board/state?repo=owner/name`
- `POST board/sync { repo }`
- `POST board/selection { repo }`
- `POST board/implement { issueId }`

All Board routes are guardian-only. Task routes and Manager identity/runtime
semantics are otherwise unchanged.
